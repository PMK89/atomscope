# ADR 0003: Renderer foundation

Status: ACCEPTED

## Context

Avogadro 1 parity needs: wireframe, stick, ball-and-stick, van der Waals spheres, labels, axes,
unit cells, force/dipole vectors, hydrogen bonds, ribbons/cartoons, ring polygons, multiple
translucent isosurfaces with independent isovalues and colors, orbital lobes (+/-), per-atom
picking, box/lasso selection, measurement overlays, orthographic and perspective cameras,
screenshots, and performance with 10^4 to 10^5 atoms and grids of 10^7 voxels.

## Decision

Build the renderer on Three.js (WebGL2) with project-owned primitives:
- `InstancedMesh` spheres and cylinders for atoms/bonds (one draw call per representation),
  colors and radii in per-instance attributes, GPU picking via an ID render target.
- Isosurfaces generated by marching cubes in a Web Worker (transferable ArrayBuffers), rendered
  as indexed `BufferGeometry` with optional transparency sorted per surface.
- A scene graph of "display layers" (Avogadro "engines" equivalents) each owning its Three.js
  objects, driven by an immutable structure snapshot plus a layer settings object.
- Camera controller supporting trackball rotation, pan, zoom, orthographic/perspective switch,
  and "fit to selection".

## Alternatives considered

- Mol*: best-in-class rendering, but its state/plugin model is heavy and editing tools would fight
  its representation pipeline. Kept as an inspiration for volumetric rendering.
- 3Dmol.js: used by the prior workbench; limited volumetric control, no workers, opaque picking.
- WebGPU-only: not yet universally available; Three.js gives a WebGPU path later.

## Consequences

- We own a moderate amount of graphics code, which needs its own unit tests (geometry, picking
  math, marching cubes against analytic fields) and performance fixtures.
